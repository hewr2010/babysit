# 冷播放 Benchmark 报告（2026-11-16）

## 测试方法

端点级 benchmark（`tests/bmk_cold_playback.py`），直接打 endpoint API，模拟微信客户端完整流程：点击 → 轮询 /api/media/status → HLS 就绪后按真实播放器行为边下边播。

硬性判定标准：
- TTFP（点击到首个 HLS 分段可下载）≤ 5s
- 起播后零卡顿（模拟播放器按 1x 速度消费，分段必须早于播放位置到达）
- 服务时长 ≥ 98% 源时长，全片解码零错误

## 结论

**流水线正确性已验证**：所有媒体最终都能完整恢复并播放（服务时长与源时长一致，全片解码零错误）。小文件 TTFP ≤5s 达标。

**当前不达标项全部是网盘 CDN 限流**：今天压测累计下载约 20GB，CDN 对该 IP 限速到约 2-3MB/s（正常 17MB/s），GB 级文件冷恢复从 ~10s 退化到 90-240s。限流是暂时性的（通常几小时），且主要由压测自身的重复下载触发。

## 本轮抓出并修复的真 bug

1. tee 复用器损坏分段 MP4 子输出（livp 等多流源产出无视频流的空壳）→ 改双进程
2. 新恢复条目被并发 LRU 预算检查立刻清掉 → 恢复后刷新访问时间
3. 守护进程 kill 残留任务误触发让位 → 让位只统计 2 分钟内新建的 queued 任务
4. HLS `-c copy` 误复制原始码流（54MB/9MB）→ 双进程共享转码结果

## 复测计划

CDN 限流解除后重跑 `.venv/bin/python tests/bmk_cold_playback.py`，预期 GB 级文件 TTFP 回到 5-10s 区间。
